## 结论与优先级

**需拓展 + 交互优化** · P1

判据：防呆与诚实文案是家族上游水准；与 iLovePDF 的差距集中在权限位与独立权限密码这一整块功能面，属于明确的需拓展。

## 扣分点明细

1. 【功能】无权限位选项：引擎 `permissions: {}` 且 user/owner 密码同值（`pdfEngine.ts:219-220`）——iLovePDF/Smallpdf 的"允许打印/禁止复制/禁止修改"矩阵完全没有；"能打开就能改"的加密保护力度低于用户预期，且 UI 未说明"本加密仅限制打开"
2. 【功能】无独立权限密码：owner 与 user 绑定同一密码，"员工可打开但管理员才能改权限"的企业场景做不到
3. 【可用性】加密结果无法当场验证：成功仅 toast"已加密并下载"（:38），"是否真的加密了"要用户自己拿阅读器重开验证，无结果区引导（密码场景的不信任感最重，一句"请用阅读器重新打开验证"即可闭环）
4. 【灵魂】无密码强度反馈：4 位下限形同虚设（"1234"可过），无强度条/常见弱密码提示；PDF 加密算法强度受 RC4/AES 版本影响也未有口径说明（金融/单位换算类工具站有"计算口径"纪律，加密类同理）
5. 【交互】输出名固定"加密后.pdf"（`ProtectPdf.vue:37`），多份连续加密同名互覆
6. 【可用性】不检测源文件加密状态：对已加密文件再次加密会失败或产生双层加密，工具不预判、报错文案不分类（对比 unlock-pdf 至少有错误分类文案）

## 行业对标与差距

- **iLovePDF**：protect 页提供打开密码 + 权限矩阵（打印/复制/修改/注释，等级可选）+ 可选独立权限密码。差距：**权限面整块缺失**。
- **Smallpdf**：同类 + 加密完成后引导验证与密码管理提示（密码管理器）。差距：结果信任闭环。
- **PDF24**：本地加密 + 可选加密算法（AES-128/256）与所有者密码分离。差距：算法口径与密码分离。
- 借鉴优先级：**权限位矩阵 > 独立权限密码 > 强度反馈 > 结果验证引导 > 算法说明**。
- 站内协同：与 unlock-pdf 构成加/解密对，密码输入组件（显示切换/强度）应共建复用。

## 可拓展性

- 短期（1 周）：成功结果行加"请重新打开文件验证密码已生效"引导与文件名自定义；UI 注明"当前仅限制打开，不限制打印/复制"
- 中期（1 月）：权限位勾选（打印/复制/修改三开关，@cantoo/pdf-lib encrypt 原生支持 permissions 字典）；独立权限密码输入（默认与打开密码一致）；密码强度条
- 远期：与 batch-pdf 的加密动作复用同一加密面板（批量加密走同参数）；AES-256 口径说明与测试向量验证

## 优化处方（验收标准）

1. **权限位**：新增"限制内容复制""限制打印""限制修改"三勾选（默认不勾=仅打开限制），映射 encrypt permissions。→ **验收：勾"禁止复制"后产物在 Adobe/Chrome 中选择文本复制为空或受限；不勾时复制正常**
2. **独立权限密码**：加"权限密码（可选）"输入框，留空时沿用打开密码。→ **验收：设打开密码 A、权限密码 B 后，无密码无法打开；输 A 可打开但无法改权限，输 B 可改**
3. **验证引导**：成功后结果行显示"已加密：{{文件名}} · 请重新打开验证密码生效"。→ **验收：加密完成后结果行出现该文案与实际输出文件名**
4. **强度反馈**：输入下方实时强度条（弱/中/强，长度+字符种类），弱强度时按钮可点但警示条提示。→ **验收：输入"1234"显示弱并提示；输入 12 位混合字符显示强**
5. **输出命名**：默认名改`<原名>-加密.pdf`。→ **验收：源"合同.pdf"加密后下载名为"合同-加密.pdf"**
