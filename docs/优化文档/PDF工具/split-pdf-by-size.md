## 结论与优先级

**交互优化** · P2

判据：65 分；算法是家族最严谨的一档（对照 compress-pdf 的目标未达成静默成功，pdfEngine.ts:976-977——本工具靠"逐页实测上界打包"结构性避免了该问题），剩余全是反馈粒度与单位细节。

## 扣分点明细

1. 【可用性】结果卡无达标判定：每卷只显实际 KB（:146-149），没有"≤ 10MB ✓"绿标；其实实测上界贪心决定了实际卷体积必然 ≤ 目标，这个保证算法层面成立但 UI 没把话说满（notice 只写"一般略小于"，:152-155）——确定性结论被写成概率性措辞
2. 【功能】仅 MB 单位（:129）：微信 200MB？邮箱 25MB？尚可用整数；但 2048KB、512KB 级目标要输 0.2/0.5 小数（min=0.1），Sejda 支持 KB/MB 切换
3. 【功能】不能只拆部分页：必须全文档参与（:57 只查总页数），"把前 100 页压进一卷"做不到，要先 extract-pdf-pages 两跳
4. 【性能】无耗时预估与取消：第一阶段逐页实测是 N 次完整 save（:63-71），notice 只说"请耐心等待"（:154），500 页文档用户只能盯着 70% 前的慢速爬升，无中断手段
5. 【交互】目标值不记忆也不给常用预设：每次进入默认 10MB（:16），缺"10MB 邮箱 / 25MB Gmail / 200MB 微信"快捷 chips
6. 【可用性】含超标页的卷不标注：单页超标只出一条一闪而过的 warn toast（:72-74），结果卡上看不出哪卷含超标页、超出多少
7. 【交互】卷文件名含全角括号与中文（:102），跨平台解压偶见编码问题；ZIP 名固定"按体积拆分.zip"（:118）不可自定义

## 行业对标与差距

- **Sejda Split by size**：KB/MB 双单位、可只拆页码范围、完成后逐卷列出"页数+实际大小"并标注是否达标。差距：单位灵活性与范围限制。
- **iLovePDF**：拆分预设（每 N 页/固定范围）+ 拖拽页选择器，虽无体积模式但入口引导更直观。差距：本工具算法更准、但入口更糙。
- 借鉴优先级：**达标绿标（把算法保证说出来）> KB 单位与预设 chips > 页码范围参与拆分 > 取消按钮**。

## 可拓展性

- 短期（1 周）：结果卡加"≤ 目标 ✓"判定与超标页标注；目标值 localStorage 记忆；预设 chips（10/25/50/200MB）
- 中期（1 月）：页码范围输入（复用 PagePickerTool 的 parsePageSpec）；第一阶段实测并行化（Worker 或分批 yield）+ 耗时预估
- 远期：与 compress-pdf 共享"目标体积"引擎（compress-pdf.md 远期已提），压缩+按体积拆分成"体积合规"组合工具

## 优化处方（验收标准）

1. **达标标记**：每卷卡显示"第 k 卷 · N 页 · X MB · ≤目标 ✓"。→ **验收：任意 PDF 拆分后所有卷均带 ✓；构造单页 20MB、目标 10MB 的样例，该卷显示"单页超限"黄标**
2. **KB 单位**：单位下拉 MB/KB，KB 时输入 2048 精确生效。→ **验收：目标 2048KB 拆分后每卷 ≤ 2048KB**
3. **范围参与**：新增"参与拆分的页"输入（空=全部）。→ **验收：填 1-50 后仅这 50 页被打包成卷**
4. **耗时预估**：第一阶段进度文案附"预计还需约 N 秒"（按已完成页耗时线性外推）。→ **验收：100 页文档运行 10 秒后出现预估且误差随进度收敛**
5. **目标记忆**：localStorage 记住上次目标值。→ **验收：改 25MB 后刷新页面仍为 25MB**
