## 结论与优先级

**交互优化 + 需拓展** · P1

判据：基础流程合格且错误处理是家族亮点，但场景覆盖缺了"owner-password-only"这最常见的一角；合规文案需补一句硬边界。

## 扣分点明细

1. 【功能-硬伤边缘】权限密码-only 文件无法处理：组件强制非空密码（`UnlockPdf.vue:21-24`），而"可打开但被限制打印/复制"的 PDF（很多机构 PDF 仅设权限密码）本无需密码即可解密重建（pdfjs 不带密码即可载入，pdf-lib ignoreEncryption 重存即去限制）；iLovePDF unlock 对此类文件直接一键解除不要求输入——本工具把最常见的合法场景拒之门外
2. 【功能】不检测加密状态：未加密文件也要求输入密码才能走完流程，无法提示"该文件未加密，无需解密"（载入后 pdfjs 首帧即可判定，信息已具备却未用）
3. 【灵魂/合规】未明说能力边界：placeholder"输入你已知的密码"（:44）与 notice 授权声明（:53-55）已到位一半，但缺"本工具无法破解或找回未知密码"这句硬边界——iLovePDF 明确写明只处理已知密码，缺少这句既不利于合规也不利于管理用户预期
4. 【交互】无显示密码切换：type=password 固定（`UnlockPdf.vue:44`），长密码输错只能盲改；同站 protect-pdf 也无强度反馈，两处应共用密码输入组件
5. 【交互】输出名固定"解密后.pdf"（`:28`），多份文件批量处理时同名互覆（本工具 single 模式一次一份，但连续处理多份时依旧）
6. 【可用性】成功后无验证引导：解密成功仅 toast（:29），提示用户"重新打开确认可正常阅读"的引导缺失（密码类操作用户天然不放心，一句确认文案成本低）

## 行业对标与差距

- **iLovePDF**：unlock 页明确两类密码（打开密码/权限密码）的教育文案，owner-password-only 一键解除；明确"无法破解未知密码"。差距：**场景覆盖 + 合规教育**。
- **Smallpdf**：同类两分支处理 + 失败原因细分（密码错误 vs 非加密 vs 权限不足）。差距：错误分类。
- 借鉴优先级：**owner-password-only 支持 > 加密状态检测与分支文案 > 能力边界声明 > 显示密码切换**。
- 站内协同：与 protect-pdf 是一对（加/解密），密码输入组件与文案口径应共建。

## 可拓展性

- 短期（1 周）：载入后用 pdfjs 判定加密状态——无打开密码直接走无密码解密路径（owner-only 场景打开）；已加密显示"该文件受打开密码保护"；未加密提示"无需解密"并禁用按钮
- 中期（1 月）：与 protect-pdf 共建密码输入组件（显示切换/大写锁定提示/强度提示）；成功结果区加"重新打开验证"引导与文件名自定义
- 远期：批量解密（多文件同密码队列）；与 batch-pdf 的加密动作对偶整合

## 优化处方（验收标准）

1. **owner-password-only 支持**：载入后检测无需密码可读时，密码输入框变为可选并注明"该文件无需打开密码，可直接解除限制"。→ **验收：拖入仅权限密码的 PDF，不输密码可直接点解密并成功打开产物**
2. **加密状态分支**：未加密文件显示"该文件未加密，无需解密"且解密按钮禁用；加密文件显示"已受打开密码保护"。→ **验收：两种文件载入后提示行分别出现，未加密时按钮 disabled**
3. **能力边界声明**：notice 追加一句"本工具无法破解或找回未知密码"。→ **验收：/t/unlock-pdf 页面含该句且位于授权声明同段**
4. **显示密码切换**：输入框右侧加眼睛图标切换明文。→ **验收：点击后输入内容明文可见，再点恢复密文**
5. **输出命名**：默认名改含源文件名（`<原名>-解密.pdf`）。→ **验收：源"合同.pdf"解密后下载名为"合同-解密.pdf"**
