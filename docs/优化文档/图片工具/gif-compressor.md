## 结论与优先级

**交互优化 + 需拓展** · P1（目标体积模式是拓展主项）

判据：结果区与反馈是 GIF 家族样板（65 分），但"目标 KB"能力站内静图侧已有成熟引擎而 GIF 侧缺席，属明确功能缺口；试参重复解码是最大交互摩擦。

整改优先序：解码缓存（快赢）→ 目标体积自动搜索 → 预览放大 → 进度数字化。

## 扣分点明细

1. 【交互-个性】试参全量重算：run() 每次都重跑 decodeGifFrames（GifCompressor.vue:56）——解码结果不缓存，调一次参数=重新解码+重新缩放+重新编码全帧，大 GIF 迭代成本被放大 3 倍
2. 【功能-对标差距】无目标体积模式：静图侧 compress-image-to-size 已有"目标 KB+质量二分"引擎，GIF 侧只有三个手动档位；notice 甚至要用户自己想策略（:154）——同站能力不对称
3. 【可用性（家族共性）】预览钉 380px（:216-221，审计底稿 GifCompressor.vue:220）：压缩决策需看清画质损失细节，380px 内 500px+ 的 GIF 等比缩后难以核对，无点击放大/全屏
4. 【功能】参数档位粗：颜色下限 32、skip 上限 5、缩放只给百分比（用户要心算输出宽度），无抖动（dither）开关——rgba4444 量化（fileExt.ts:353）对渐变 GIF 易出色带，目前无补救手段
5. 【美观】进度条 6px 无百分比数字（:168-177）：阶段文案好但数值感缺失，与 compress-image-to-size 的文字进度实践不一致
6. 【功能】减帧延迟补偿在 UI 不可见（kept delay×skip，:71）：总时长不变的设计正确但界面上无"减帧后 FPS"说明，用户误以为时长会缩短

## 行业对标与差距

- **ezgif GIF compressor**：损失度（lossy）滑杆逐档压缩、压缩前后并排播放对比、目标尺寸迭代压缩、逐参数结果表。差距：**lossy 压缩维度缺失**（gifenc 无此能力，可用调色/减帧组合逼近）与前后对比。
- **站内 compress-image-to-size**：目标 KB+二分搜索+超目标诚实警告。差距：把这套"目标驱动"交互移植到 GIF（颜色→宽度→skip 三维搜索）是最高价值拓展。
- 借鉴优先级：目标体积自动搜索 > 解码缓存 > 前后并排对比 > dither 开关 > 进度数字化。

## 可拓展性

- 短期（1 周）：解码结果缓存于 file 级 ref，改参只走编码路径；进度百分比数字化
- 中期（1 月）：目标体积模式（三维参数按"降色→缩放→减帧"顺序网格搜索，复用静图二分思路）；预览点击全屏；dither 选项
- 远期：与 gif-editor/maker 合并"GIF 工作台"共享解码层；lossy 类量化压缩算法调研（时间维度的帧差编码）

## 优化处方（验收标准）

1. **解码缓存**：文件不变时解码帧缓存复用，改参只重编码。→ **验收：首次压缩后仅改颜色数再压，总耗时较首次减少 ≥60%（Performance 面板确认无二次解码）**
2. **目标体积模式**：输入目标 KB 后一键自动搜索参数组合至 ≤目标（优先降色，其次缩放，最后减帧），过程显示所试组合轨迹。→ **验收：500KB GIF 设 200KB 目标，自动模式输出 ≤205KB 且显示 ≥3 组尝试记录；无法达成时诚实报告最接近组合**
3. **预览放大**：预览图点击弹出全屏遮罩（100vh 内自适应），Esc/点击关闭。→ **验收：1366×768 下点击预览可全屏核对画质；压缩前后可切换查看**
4. **进度数字化**：进度条旁显示"72% · 第 36/50 帧"。→ **验收：压缩期间文案逐帧刷新，与进度条一致**
5. **dither 开关**：选项区加"抖动（减轻色带）"开关默认关，透传 gifenc 量化配置。→ **验收：开启后渐变类 GIF 色带在放大对比下减轻，体积增加可接受（≤10%）**
