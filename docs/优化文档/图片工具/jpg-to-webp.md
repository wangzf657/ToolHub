## 结论与优先级

**交互优化** · P1（编码 MIME 校验为疑似功能缺陷，优先修复）

判据：场景刚需+desc 诚实（61 分），但 Safari 无 canvas WebP 编码时的静默回退属正确性隐患，应先于交互项处理。

整改优先序：MIME 校验（疑似缺陷）→ 家族结果列表与压缩率报告 → 无损开关 → wasm 编码器。

## 扣分点明细

1. 【可用性-硬伤（家族级）】完成即自动下 zip、无结果预览（ImageConvertTool.vue:55；M-12），整改见 png-to-jpg.md 处方 1
2. 【功能-疑似缺陷】输出不校验 MIME：HTML 规范下 canvas.toBlob 遇不支持的类型静默回退 PNG（imageEngine.ts:103-115 未检测返回 blob.type），Safari 未实现 canvas WebP 编码——产出按 .webp 命名的 PNG 文件（ImageConvertTool.vue:51 直接按 target 取后缀），下游网站部署后部分浏览器照样打不开
3. 【功能】无编码参数：浏览器内置编码器不可调 effort/方法，也无"无损 WebP"开关（canvas.toBlob 不传 quality 即 Chrome 无损编码，引擎已具备实现条件 imageConvert.ts:49）
4. 【灵魂-反馈缺失】desc 承诺"体积更小"却无前后体积展示（:44-51 拿到了输入 File 与输出 Blob 却不比较）——家族处方 1 的体积对比对本工具价值最大
5. 【灵魂】质量-体积权衡无可视化：拖动滑条看不到体积变化（Squoosh 实时显示编码后字节数与画质对比），用户只能盲调 90%→85% 重跑
6. 【交互（家族共性）】文件列表无缩略图（FileDrop.vue:97-107）、无逐张重转——与 png-to-jpg.md 扣分点 3/7 同源
7. 【美观（家族共性）】进度条 6px 无百分比（:114-119），与 FfBase 百分比进度（全站最佳实践）不一致
8. 【功能（家族共性）】批量超 50 张静默截断（FileDrop.vue:28-29 直接 slice，无提示）——网站优化场景常一次拖整包切图，超出部分被静默丢弃

## 行业对标与差距

- **Squoosh**：WebP 走 wasm 编码器（不依赖浏览器实现），质量滑条实时看体积与前后画质分屏对比。差距：编码兼容性（它没有假 WebP 问题）与权衡可视化代差。
- **TinyPNG**：JPG/PNG 批量 20 张直接出 WebP，附压缩率汇总。差距：体积报告（本工具连单张对比都无）。
- 借鉴优先级：输出 MIME 校验 > 结果列表体积对比 > 无损开关 > wasm 编码器（P2）。

## 可拓展性

- 短期（1 周）：run 后校验 `blob.type === target`，不符时警告并按真实类型命名；家族处方 1-3 落地
- 中期（1 月）：加"无损 WebP"开关（不传 quality）；结果区显示单张与整批压缩率汇总
- 远期：接 Squoosh 式 wasm WebP 编码器（懒加载，跨浏览器一致输出）；并入家族"图片格式转换工作台"

## 优化处方（验收标准）

1. **输出 MIME 校验（疑似缺陷修复）**：convertImage 返回后检查 blob.type，与目标不一致时 toast"当前浏览器不支持 WebP 编码，已改输出 PNG"且文件名后缀跟随实际类型。→ **验收：在未实现 WebP 编码的浏览器转换后，得到 .png 文件与明确提示，不再出现假 .webp**
2. **压缩率汇总**：结果列表每行"原 X KB → Y KB（省 Z%）"，顶部显示整批平均节省比例。→ **验收：3 张 JPG 转 WebP 后逐行体积与平均节省率可见（随家族处方 1 落地）**
3. **无损 WebP 开关**：勾选后编码不传 quality 参数。→ **验收：同一 PNG 源勾选无损后输出体积大于有损档且解码回读像素一致（Chrome）**
4. **家族处方 1-3 落地**（结果列表、自动下载默认关、进度带百分比）。→ **验收：同 png-to-jpg.md 处方 1-3**
