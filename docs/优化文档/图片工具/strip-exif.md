## 结论与优先级

**交互优化** · P1（补验证闭环 + 批量 + 副作用披露）

判据：功能内核（重编码清元数据）可靠，缺的是"证明清干净了"的闭环与批量能力，属交互/补功能层改造，不动架构。

整改优先序：清除验证回读（P0 级快赢，引擎现成）→ 结果预览区 → 批量 → 副作用披露。

## 扣分点明细

1. 【可用性-硬伤（模式 F 家族共性）】结果零预览：run() 直接 `saveBlob`（StripExif.vue:30），DOM 无任何成品图节点——"发图更安心"的工具让用户最不安（92% 重编码画质、方向、色彩全未知）
2. 【功能】无清除验证闭环：输出 Blob 从不回读 EXIF（readExif 引擎现成，imageEngine.ts:643），"已清除"只是 Canvas 重编码的推断；与 exif-viewer 也无互链复核——exif.tools 清除后即时回显"剩余元数据：无"
3. 【功能】仅单文件（FileDrop `:multiple="false"`，:45）：批量导出游照场景一次一张，重复劳动
4. 【可用性-副作用未披露】重编码同时抹掉 Orientation 与 ICC 广色域配置：decodeToCanvas（imageEngine.ts:31-46）不做方向转正，方向错误的原片输出后不再自动转正、Display P3 照片降为 sRGB——hint（:48）只字未提
5. 【功能】无保留字段选项：版权（0x8298）/作者（0x013b）想随图带走做不到，摄影师署名场景被迫二选一
6. 【交互】对比锚点缺失：徽章只给文件体积差（:71），不显示"EXIF 本体占多少"（通常几十 KB）——用户无从得知这次清洗的真实收益
7. 【美观】成功后页面无成品区，下半屏空白；结果区样式与 gif-compressor 的统计卡（其 :141-148）水准不一致

## 行业对标与差距

- **exif.tools**：查看/清除双 Tab，清除后自动回读列表逐项标注"已移除"，支持勾选保留 GPS 以外字段、批量处理。差距：**验证闭环**（清完要能证明）与**选择性移除**两块。
- **站内 exif-viewer**：同一引擎可读 ~20 标签含 GPS 字段名。差距：清除完成后理应互链"去查看器复核"，现在两工具互相不知道对方存在。
- 借鉴优先级：清除后回读验证 > 结果预览 > 批量 > 保留字段。

## 可拓展性

- 短期（1 周）：生成后对输出 Blob 跑 readExif 回读并显示"0 条 ✓"；结果区互链 exif-viewer
- 中期（1 月）：批量模式+结果列表（每行前后体积+单独下载）+ZIP；保留字段白名单（重写 JPEG APP1 只保留指定 tag，纯前端可行）
- 远期：与 exif-viewer 合并为"照片隐私工作台"（查看→清除→复核一页完成，模式 E）

## 优化处方（验收标准）

1. **清除验证回读**：生成后对输出 Blob 调 readExif，结果区显示"回读 EXIF：0 条 ✓（原片 N 条，含 GPS：是/否）"。→ **验收：iPhone 直出含 GPS 的 JPG 处理后验证行显示 0 条且原片条数>0；空验证行不出现**
2. **结果预览**：处理后成品图内嵌显示（objectURL），支持与原图左右切换核对。→ **验收：处理后无需打开下载文件即可见成品图，方向异常照片的转正状态肉眼可判**
3. **批量模式**：multiple=true + 逐行结果列表（原图体积→新体积+单独下载）+ ZIP 打包。→ **验收：拖入 5 张照片输出 5 行结果与 1 个 zip，自动下载不再默认发生**
4. **副作用披露**：hint 或处理前 notice 注明"输出将按重编码重写：方向按像素原样、色彩配置文件将被移除"。→ **验收：拖入带 Orientation 标记的照片时提示可见，文案与实际行为一致**
5. **EXIF 占比参考**：对原片回读统计体积估算（EXIF 段长度），徽章区补"其中元数据约 X KB"。→ **验收：含大 EXIF 的相机原片显示占比，无 EXIF 的 WebP 显示"约 0 KB"**
