## 结论与优先级

**交互优化** · P1

判据：无个性硬伤；方向自动检测与进制联动是明确的体验/功能增量。

## 扣分点明细

1. 【可用性-硬伤·家族】双 textarea 各钉 180px、无同步滚动（`base.css:164-168`；M-06），详见 `pinyin-converter.md` 扣分 1
2. 【交互】方向手动切换（`registry.ts:523-525`）：无自动检测——输入仅含 0/1/空格时理应自动判为 decode，现需手动切换且默认方向直接输出错误结果
3. 【功能】无 7 位分组与自定义分隔符：老 ASCII 教材/部分课程用 7 位口径（textmechanic 同类工具支持 7/8 位与逗号分隔），本工具仅 8 位空格分组（`textEngine.ts:354`）
4. 【功能】无进制联动：想同时看 hex/dec 需另开工具——cryptii 的多编码 brick 同屏联动是标准体验；站内 developer 分类 EncodingConverter 也无二进制联动入口
5. 【可用性】解码对 >255 字节直接抛错（`textEngine.ts:359`）：16 位分组输入只得到一句"只允许 8 位 0/1"，不提示"疑似 16 位分组，可两两一组拆分"——错误可理解性打折
6. 【灵魂】无字节数/位数统计徽标（"一个汉字=3 字节 UTF-8"是教学场景高频好奇点）；无每字节一行/无空格紧凑式输出格式
7. 【交互】方向选择不记忆（TextTool.vue:19-24 initOpts 无持久化），decode 用户每次都要手切
8. 【灵魂】空态沿用通用 placeholder（`TextTool.vue:112`），无"试试输入中文看 UTF-8 字节"式的引导示例

## 行业对标与差距

- **cryptii.com**：Text/Binary/Hex/Dec 多 brick 同屏联动，改一处全线更新——编码转换"探索式"体验标杆。差距：多格式联动视图。
- **textmechanic.com**：7/8 位、逗号分隔等口径选项。差距：口径宽度。
- 借鉴优先级：方向自动检测 > hex 联动行 > 字节统计 > 16 位分组容错提示。

## 可拓展性

- 短期（1 周）：方向自动检测（正则判断仅含 0/1/空格）；输出行加字节数徽标
- 中期（1 月）：输出下方联动 hex 行（一行二进制一行 hex）；7 位模式与分隔符选项
- 远期：与 EncodingConverter 合并口径或互链（二进制/hex/base64 一站式）

## 优化处方（验收标准）

1. **方向自动检测**：输入仅含 [01\s] 时自动切 decode 并高亮选项 → **验收：粘贴 "01001000 01101001" 直接输出 Hi，无需手动切换**
2. **hex 联动行**：编码输出下方追加灰色 hex 行（每字节十六进制） → **验收：输入 "Hi" 同屏显示 "01001000 01101001" 与 "48 69"**
3. **字节统计徽标**：io-head 显示"N 字节 / 8N 位" → **验收：中文"你"显示"3 字节 / 24 位"（UTF-8 口径）**
4. **16 位分组容错**：检测到 16 位串时提示"疑似 16 位分组"并给出按 16 位拆分的结果 → **验收：粘贴 16 位串不再仅报错，而是可解析可还原**
5. **输出格式选项**：新增"空格分组/紧凑/每字节一行"三选 → **验收：三种格式输出均可被本工具 decode 正确还原**
