## 结论与优先级

**交互优化** · P1（编辑区 96px/140px 是可用性硬伤级，但功能骨架是分类最佳）

判据：SQL 编辑框 + 错误条合计不到 250px，写复杂 JOIN 无法通览——与工具"写 SQL"的定位直接冲突。

## 扣分点明细

1. 【可用性-硬伤】SQL 编辑框 140px + 错误提示区 96px（`SqlQuery.vue:224,303`；共性-根因 2）——写 20 行 JOIN 查询时编辑框只显示 5~6 行，错误长信息被 96px 截断，定位"编辑器"体验不可接受
2. 【功能】无表结构预览：加载文件后看不到列名/类型/行数（要 SELECT * 手动探），DuckDB 的 DESCRIBE 是标配
3. 【交互】慢查询无取消按钮、无耗时统计（alasql 大表 JOIN 分钟级，用户只能干等刷新）
4. 【功能】结果 500 行预览上限（:173 toast 披露，诚实）但无"下载全部"与"预览 500 行"的界限说明在结果区（只在 toast 里一闪而过）
5. 【灵魂】无查询历史（localStorage 存最近 10 条）；表名注册规则（文件名→表名，去扩展名/中文字符处理）未在 UI 披露

## 行业对标与差距

- **DuckDB WASM Shell**：完整 SQL 方言+窗口函数+Parquet 直查+`.mode` 切换。差距：**方言能力代差**（架构性，alasql 上限如此，诚实标注）。
- **sqlime.org**：schema 面板+查询历史+自动补全。差距：编辑器辅助。
- 借鉴优先级：**编辑器弹性高度 > 表结构面板 > 查询历史 > 耗时+取消**。

## 可拓展性

- 短期：SQL 编辑框改 `min(280px, calc(100vh - 520px))`；错误条不限高（最多 8 行）；查询计时显示
- 中期：表结构面板（列名/行数/类型推断 chip）；localStorage 查询历史 10 条
- 远期：换 DuckDB WASM 引擎（懒加载 5MB，窗口函数+Parquet 直读——注意懒加载纪律），保留 alasql 作为轻量档

## 优化处方（验收标准）

1. **编辑器弹性**：SQL textarea 高度 `min(280px, calc(100vh - 520px))` 且可拖拽。→ **验收：1366×768 下 20 行 JOIN SQL 完整可见无需编辑框内滚动**
2. **表结构面板**：文件加载后在编辑框上方显示每表 chip（表名+行数+列名 tooltip）。→ **验收：加载 2 表后出现 2 个 chip，hover 显示列清单**
3. **耗时+取消**：查询按钮执行中变"取消"，完成后 toast 附耗时。→ **验收：慢查询可取消恢复交互；toast 显示"1.2s"**
4. **查询历史**：编辑框上方历史 chips（最近 10 条，点击回填）。→ **验收：执行 3 条查询后出现 3 个历史 chip，点击回填 SQL**
